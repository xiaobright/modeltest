## 1. 为什么 V4.1b 停更：尺子已经失去区分度

V4.1b 的初衷是「在真实渠道、成本与额度约束下，为个人开发/选型提供一份参考台账」。
到 2026-09-10，这个目的已经达成，而且**区分度接近见顶**：

- **顶端拥挤。** 98 分档已同时站着 GPT-5.6-sol、DeepSeek-V4.1-Flash、GLM-5.3-Flash；
  94–98 分区间挤满了各家主流模型（DeepSeek-V4-Pro 灰度/DSH、GLM-5.3、Mimo-X-Flash、
  GPT-5.6-terra、Kimi-K2.7 等）。轻量/免费模型也普遍能到 92–94。
- **剩余方差是琐碎项，不是能力项。** 当前丢分基本只剩两类：
  - `V4-F12-04`：授权失败语义串返回 `not_authenticated` 还是
    `not_authorized_for_target`，是模型措辞偏好，DS/GLM/Gemini 家族通病；
  - `V4-F8-08`：代码里有没有随手断言 `wifi_ssid` 之类的静态契约。
  这两项测不出工程能力高低，只是运气与习惯。
- **成本塌到几乎免费。** 从早期 GPT-5.6-sol 一枪约 60 元，到 DeepSeek-V4.1-Flash
  限时半价 23.71 积分 ≈ **¥0.47**、Mimo-X-Flash **免费 7 分钟 94 分**。工程大模型已
  从「高成本探索」变成「几毛钱日用消耗品」。
- **结论稳定。** 最新一轮（GLM-5.3-Flash 98、DeepSeek-V4.1-Flash 98、Mimo-X-Flash 94）
  没有带来任何推翻既有判断的新信息，只是再次确认了 94–98 的天花板。

一句话：**尺子本身没有坏，但已经量不出新东西了。** 继续追加样本只是在同一个饱和区间
里重复报数，因此主动停更，不再追加观测。

**最后一次追加观测：** DeepSeek-V4.1-Flash @ WorkBuddy（`20260910_122044`，98/98/B+）。
本条并入后，V4.1b 台账封笔。

## 2. V5 的三次失败尝试

为了让「综合工程能力尺」比 V4.1b 更进一步，先后做过三次 V5 尝试，全部失败。完整证据、
题源、契约与评测器分别归档在 `modeltest` 与独立仓库 `modeltest-v5`。

### 第一次：sleepgw 状态机专项（2026-07-29 冻结）

- 目标本是综合工程能力尺，实际做成「照规格从零实现睡眠网关状态机」的纯 Python 专项。
- 两个顶级模型（GLM-5.2、DeepSeek-V4-Pro）都拿 **29/29 满分**，且输出几乎相同——
  任务天花板被顶级模型摸到，无法区分高低。
- 评分用了「自指 Oracle」（期望值 = 跑正确版后冻结），校准永远发现不了正确版自身的错误。
- 归档：`modeltest/archives/v5_specialty_frozen_20260729/`

### 第二次：FRESH-1 遥测协议题（2026-08-01 冻结）

- 想做 V4.1b 高级版，实际缩成「修 5 个人造缺陷」的小题。
- 最弱模型 4 分钟就满分，反超强模型；缺陷由正确版反推注入，与公开事故一一对应，
  模型只需恢复 5 个局部分支，不需要高级工程改造。
- 评分有偏差：已确认 ACK 的事件被强制重新投递，奖励了错误行为，导致弱模型反超。
- 花了约 10 美元跑付费强模型，没产生可用排名。
- 详细教训与重启约束：`modeltest-v5` 仓库 `docs/FAILURE_LESSONS.md`
- 归档：`modeltest/archives/v5_formal_failed_frozen_20260801/`

### 第三次：V5.0 综合整改题（2026-08-31 封存）

- M1–M5 的题源、契约、隔离与 evaluator 治理均已完成，工程测试装置本身可用。
- 廉价 M6 探针结果：`hy3 = 54/100`，`glm-5.3-flash = 98/100`。
- 关键问题：GLM-5.3-Flash 在 V5 拿 98，在 V4.1b **同样是 98**；顶端再次接近饱和，
  V5 没有打开新的顶端区分带宽。
- 因此停止剩余 M6 探针，不进入 M7–M9，不改题、不调权重、不重算历史评分。
- 封存说明：`modeltest-v5/docs/_archive/v5_current_frozen_20260831/PROJECT_FROZEN.md`

### 共同教训

1. **专项冒充综合**——都偏离「广覆盖综合工程维护尺」，缩成单一机制专项。
2. **检测器当刻度尺**——能测出「会不会」，测不出「谁更强」。
3. **评分标准自身有 bug**——自指 Oracle、投递偏差，被误当成能力差异。
4. **顶端无法区分**——第一次顶级模型满分饱和，第二次弱模型反超，第三次顶端再次饱和。
5. **认知闭环风险**——由模型参与出题、再由同类模型施工，存在明显的能力上限与循环性。

## 3. 不会再有新的评测版本

综合以上，本项目到此为止：

- **不开发 V4.1c，不开发 V5，不开发 V5 HIL。** 「新鲜度 / 显式 session / QEMU / HIL」
  等题源仅作为远期备忘保留，不进任何现行评测。
- **不修改 V4.1b 的评分逻辑与题面**（`score_model.py`、`rubric.md`、`item_registry.json`、
  `evaluator/tests/hidden/` 已于 2026-07-19 以 SHA-256 冻结）。
- **不用 V4.1b 规则重算历史正式成绩**，不跨版本回填或混排。
- **原因不止是「不需要」，也是「力不能及」：** 要突破当前顶端饱和，需要一套真实、
  高耦合、跨语言（C/C++ + Python + 协议 + 硬件）、且不依赖模型自出题的综合题；这已经
  超出个人在时间、硬件与预算上的可持续投入能力。与其勉力造出又一个会被顶端打满的
  专项，不如在 V4.1b 这份已经稳定、可复算、证据完整的台账上收工。

**V4.1b 继续作为最后一份有效的综合能力主尺。** 它不是「没做完」，而是「到站了」。
