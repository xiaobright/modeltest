# Project2 V4 最终评测与 V2 对照分析

**日期：** 2026-07-12  
**基准版本：** V4.0 frozen  
**样本：** 18 个独立模型身份，25 次正式运行  
**正式成绩：** `evaluator/reports/v4_scoreboard.md`

---

## 1. 口径

V4 的一行结果应理解为：

```text
model + provider/endpoint + billing tier + channel + harness + thinking level + environment
```

同名模型经不同供应端点交付时，不默认视为同一个可直接比较的模型实例。V2 与 V4
的题目、rubric 和证据链也不同，因此跨版本原始分数只用于定位能力结构变化，不能
单独证明模型升级或退化。

V4 使用两个核心分数：

- **Ability**：交付代码和工程闭环的完成度。
- **Ship/Class**：信任、安全和发布风险。

## 2. 总体结果

| 指标 | V2 frozen | V4 current |
|---|---:|---:|
| 正式运行 | 24 | 25 |
| Ability/总分均值 | 82.62 | 87.78 |
| 中位数 | 82 | 90 |
| A / B+ / B / D | 单分体系 | 6 / 8 / 9 / 2 |
| 满分 Gold | 无 | 100 / A |

V4 均值更高不能解释为题目更简单。本轮加入了多个 GPT-5.6 型号和思考强度样本，
样本分布明显偏向前沿模型。对 13 组近似可配对结果做描述性统计，原始分差平均
约 +0.08、中位数 +2，但范围达到 -14 至 +14。更合理的解释是：V4 重排了模型，
而不是统一抬分或压分。

当前顶部为 GPT-5.6-sol/luna xhigh 99，Gold 为 100。顶部可达，量表不是理论满分。

## 3. V4 相对 V2 的有效改进

### 3.1 82 分墙被拆除

V2 的 ambient/current-session 缺口会把大量风格不同的模型压到 82。V4 主榜中明确
带 `S-ambient` 的运行有 16/25，Ability 已分布在 76 至 92：Qwen 76、GLM/Grok
81-82、M3 84、HY OpenCode 86.5、Kimi 90、GPT-5.5/Composer/HY WorkBuddy 92。

ambient 仍是最常见的概念卡点，但不再是数值硬墙。

### 3.2 Ability/Ship 双轨证明有必要

Gemini-3.1-Pro 的 Ability 为 90，但因明文密码和错误认证行为触发 Ship 60、Class D。
这类结果说明“完成了大量工程工作”和“可以发布”是两个问题。V2 的单一总分难以
诚实表达这种形态。

### 3.3 迁移题开始区分真实工程能力

旧表补列、`ts` 回填、索引创建顺序、幂等初始化和混合排序使 Grok、GLM、Qwen
暴露出 crash/fidelity 缺口。V2 中一些高分提交没有被这些场景充分覆盖。

### 3.4 F9 证据链更可信

ESP static 与真实 build 已分离。正式 F9 满分要求 result-local build log、固件、
size 和 SHA256；仅有静态 marker 或共享 build 目录不再足够。

这张表展示的是诊断变化，不是模型版本排行榜。

### 4.1 GLM 与 Kimi/Composer 的排序反转

V2 表面上 GLM-5.2 整体强、Kimi/Composer 偏弱；V4 则由 Kimi 90、Composer 92 高于
GLM 三渠道 81-82。还原评分和渠道后，反转由三部分组成：

- Kimi K2.7 的 V2 未封顶小计约 88，正式 82 主要是 ambient hard cap；V4 90 仅是
  小幅真实提升，大部分变化来自 V4 恢复表达其广泛完成度。
- Composer V2 未封顶约 81-83，V4 则真正修好 migration、no-actor、voice 和 ESP，
  因此 92 包含约 9-11 分的实质运行质量提升。
- GLM V4 三渠道共同漏 ambient（含 care context 连带约 7 分）并发生 migration crash；
  加回 ambient 后约 88-89，接近 V2 非满血渠道。V2 的 95 是硅基流动满血 API，V4
  没有同 provider/product 对应样本。

V4 还去除了 reference 对 explicit session/current-session 解法的直接剧透。现有结果提示
模型画像可能不同：GLM 在明确契约下执行力强，Kimi/Composer 本轮在全仓覆盖和自主收口
上更好。该观察用于指导后续把“契约执行、隐含风险发现、跨模块收口”分维度测试，不足以
单独证明模型本体升级或退化。

## 5. GPT-5.5：“能力退化”与“磨洋工”应分开

### 5.1 最终代码能力

GPT-5.5 在 V4 得到 92/B+。Auth、voice、migration、sleep、ESP static 和真实 build
基本完整，主要漏项是 ambient 和一项 reason 精度。因此没有证据支持“广泛的代码
能力崩塌”。

### 5.2 代理执行效率

执行过程存在明显的重复表述、工具调用前迟滞和无效 token 消耗。操作者确认 V4
计费接近完美缓存命中，最终仍花费 $9.06。

| 同一 V4、xhigh | Ability | 时间 | 花费 |
|---|---:|---:|---:|
| GPT-5.5 | 92 | 约 23 min | **$9.06** |
| GPT-5.6-sol | 99 | 约 24 min | $7.25 |
| GPT-5.6-luna | 99 | 约 24 min | $2.11 |

在相同时间量级下，5.5 比 sol 贵约 25%，比 luna 贵约 4.3 倍，但少 7 分。即使完全
不引用 V2，这也支持“agentic execution efficiency regression”。

### 5.3 V2 历史成本与缓存补证

历史线程 `019eaaac-4d46-7110-976b-5fd3c472f712` 的回合
`019ec157-ff65-7c72-a3cd-9586bc36c241`（“计算5.5理想缓存成本”）确认该讨论发生在
V2 后期、V3 设计开始之前。

| V2 运行 | 请求 | 新增输入 | Output | 缓存命中 | 总 token | 实际成本 | 命中率 |
|---|---:|---:|---:|---:|---:|---:|---:|
| GPT-5.5 | 99 | 121.7 万 | 5.606 万 | 1152.7 万 | 约 1280.1 万 | **$13.5298** | 90.5% |
| GPT-5.4 | 119 | 61.8 万 | 8.3 万 | 1641.5 万 | 约 1711.6 万 | **$6.8870** | 96.4% |

若 GPT-5.5 达到 GPT-5.4 的 96.4% 缓存命中率：

- 输入侧总量约 1274.4 万；
- 理想新增输入约 45.9 万；
- 理想缓存命中约 1228.5 万；
- 约 75.8 万 token 本应走缓存却按新增输入计费；
- 理想成本约 **$10.12**，缓存中断/分段带来的额外成本约 **$3.41**。

这说明 V2 的 $13.53 高价有约四分之一来自缓存维持失败；在理想缓存下，5.5 当时
应约为 10 美元，而不是 13.5 美元。

### 5.4 价格倍率归一化

| 对比 | 5.5 / 5.4 成本比 | 按 2 倍单价粗略折算后的工作量比 |
|---|---:|---:|
| V2 实际 | 1.96x | 0.98x |
| V2 5.5 理想缓存 | 1.47x | 0.73x |
| V4 实际 | **3.62x** | **1.81x** |

这里按当前记录的 5.5 与 5.4 输入/输出单价约 2:1 做粗略归一。V2 理想缓存下，5.5
完成任务所需的价格归一化工作量约为 5.4 的 73%；V4 则升至约 181%。因此 V4 总钱
虽然比 V2 实际值少，但 5.5 相对 5.4 的成本差距显著扩大，不能只用价格倍率解释。

从跨版本降幅看，这个分化更直观：

| 模型 | V2 实际 | V2 理想缓存 | V4 实际 | V4 / V2 实际 | V4 / V2 理想缓存 |
|---|---:|---:|---:|---:|---:|
| GPT-5.5 | $13.5298 | $10.12 | $9.06 | 67.0%（下降 33.0%） | 89.5%（下降 10.5%） |
| GPT-5.4 | $6.8870 | — | $2.50 | 36.3%（下降 63.7%） | — |

也就是说，V4 总成本下降主要是任务执行量和缓存状态共同改善，不是单价倍率发生了
有利变化；而 5.4 的降幅远大于 5.5。5.5 在 V2 的缓存异常被校正后本应约 $10.12，
V4 完美缓存下仍需 $9.06，节省其实只有约一成；同期 5.4 则节省近三分之二。这种
不对称才是 V4 中成本比从 1.47x 扩大到 3.62x 的直接原因，也与重复表述、延迟调用
工具的过程观察一致。

V1 归档的 `first_round_report.md` 还记录过另一组部分统计（5.4 $6.4362、5.5
$9.8866），但它明确是“另一轮统计”，token 口径也不同，不作为这组 V2 缓存计算的
主数据。其定性观察是当时的 5.5 更收敛、读得少；这与 V4 的重复输出和工具调用迟滞
形成反差。

因此正式结论是：

> GPT-5.5 的最终代码能力仍强，但代理执行策略和缓存归一化成本表现出明显退化。
> “降智”主要体现为磨洋工，而不是不会完成工程任务。

## 6. GLM-5.2：OpenCode 是 harness，不是 provider

操作者补充的供应链信息如下：

| 版本 | Model | Provider/产品 | Harness | Ability |
|---|---|---|---|---:|
| V2 | GLM-5.2 | 硅基流动按量计费、满血 API | OpenCode | 95 |
| V4 | GLM-5.2 | OpenCode Go 订阅端点 | OpenCode | 82 |
| V4 | GLM-5.2 | WorkBuddy 免费端点 | WorkBuddy | 81 |
| V4 | GLM-5.2 | Qoder 免费端点 | Qoder | 81 |

因此 V2 95 到 V4 82 不能写成“同渠道下降 13 分”。OpenCode Go 订阅结果与两个免费
端点仅差 1 分，现有数据支持“订阅端点没有发挥硅基流动满血 API 的上限”。社区所说
的量化是合理假设，但在 provider 未披露模型精度前，不能仅凭成绩证明量化事实。

后续 meta 至少增加：

```text
model
provider
endpoint_product
billing_tier
channel
harness
thinking_level
```

## 7. 思考强度与性价比

GPT-5.6-sol 在同一 V4 上形成 medium 91、high 98、xhigh 99 的单次梯度。当前观察中，
high 是较好的成本/质量平衡点，luna high 是最佳单次价格结果。

但这些还不是稳定统计结论：每档只有一次正式运行，而且 terra high 97 反而高于
terra xhigh 95，已经显示随机性和执行路径方差。报告应使用：

- “当前单次观测最佳”；
- “observed Pareto point”；

而不是“日常无脑选”或“已经证明 high 必然最优”。关键档位至少重复 3 次，再报告
均值、范围、成功率和到达 A 类的成本。

## 8. V4 仍未完全解决的问题

V4 已明显改善中游区分，但 81-82 仍有 7 个运行聚集。现在的聚集不是硬 cap，而是
多个模型真实共享 ambient + migration/voice 缺口。

顶部 95-99 的差异主要来自 F12 reason、ESP CMake/topic marker、voice bridge 和报告
完整性。它更擅长测收口、注意力和工程纪律，尚未充分测到复杂架构耦合上限。
`docs/v4/archive/original_design/CAPSTONE_ITEM_IDEAS.md` 中的高耦合题仍适合作为
V4.1+ 的独立扩展，但不应在当前
冻结量表内临时加分。

## 9. 下一轮数据要求

每次运行除现有 meta 外，应保存：

- 原始输入 token、cached input、输出 token、reasoning token；
- 实际费用、零缓存估算、完美缓存估算；
- 首次工具调用时间、首次有效编辑时间；
- 无状态变化回合数、重复文本回合数、失败重试数；
- provider、endpoint、订阅/按量层级和模型精度声明；
- 同配置重复运行编号。

这样可以把“磨洋工”“渠道缩水”“思考强度收益”从体感升级为可复核指标。

## 10. 阶段结论

1. V4 成功拆除了 V2 的 82 硬墙，并增加了可信的迁移、信任和 build 证据。
2. Ability/Ship 双轨是必要设计，Gemini-3.1-Pro 90/60/D 是最典型证明。
3. GPT-5.5 的问题主要是代理执行效率退化，不是全面代码能力崩塌。
4. GLM-5.2 的 95 与 82 来自不同 provider/产品层，不能归因于模型本体或 V4 难度。
5. 当前成本和思考强度结论仍是单次观测，需要重复运行建立方差。
6. 顶部仍偏向细节收口；下一阶段若继续改题，应优先加入独立 capstone 耦合题。
